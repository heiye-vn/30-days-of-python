# 数据库学习文档 - 性能优化与对比篇

## 第十一章 性能优化

> 前十章我们从数据库基础到表设计，从 SQL 语法到事务锁，从 Python 操作到 Redis 配合，走完了"会用"的阶段。
> 本章是"用好"阶段——当数据量从几千涨到几百万、当并发从个位数涨到上千，你必须知道怎么让数据库"跑得快"。
> 性能优化不是玄学，它是一套有章可循的方法论：先定位问题（EXPLAIN / 慢查询日志），再分析原因（索引 / 表结构 / 查询写法），最后实施优化。

前端类比：这就像前端做性能优化——先用 Chrome DevTools 的 Performance 面板录制火焰图定位瓶颈，再决定是减少重排重绘、懒加载组件、还是用虚拟列表。数据库的 EXPLAIN 就是"火焰图"，慢查询日志就是"性能面板"。

## 11.1 查询优化

### 11.1.1 EXPLAIN 执行计划解读（MySQL vs PostgreSQL）

EXPLAIN 是数据库提供的"查询计划分析器"。你在任何 SELECT 语句前加上 EXPLAIN 关键字，数据库不会真正执行查询，而是告诉你"它打算怎么执行这个查询"——用不用索引、走全表扫描还是索引扫描、预计扫描多少行、用了什么连接策略。

前端类比：这就像你在浏览器里看 Network 面板，一个请求的 Waterfall 展示了 DNS 解析、TCP 连接、请求发送、等待响应、内容下载各阶段耗时。EXPLAIN 展示的是 SQL 查询的"执行瀑布"——数据库内部的执行步骤和成本估算。

#### MySQL 的 EXPLAIN 输出

```sql
-- 准备数据：一张 100 万行的订单表
-- 假设 orders 表有 id, user_id, status, amount, created_at 字段
-- 在 user_id 上有索引 idx_user_id

EXPLAIN SELECT * FROM orders WHERE user_id = 50000 AND status = 'paid';
```

MySQL EXPLAIN 输出格式（表格形式，每行一个访问步骤）：

```
+----+-------------+--------+------------+------+---------------+--------------+---------+-------+------+----------+-------------+
| id | select_type | table  | partitions | type | possible_keys | key          | key_len | ref   | rows | filtered | Extra       |
+----+-------------+--------+------------+------+---------------+--------------+---------+-------+------+----------+-------------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_user_id   | idx_user_id  | 8       | const |   15 |    33.33 | Using where |
+----+-------------+--------+------------+------+---------------+--------------+---------+-------+------+----------+-------------+
```

逐列解读：

| 列名 | 含义 | 关注重点 |
|------|------|----------|
| id | 查询的序号，相同 id 表示同一组，从上往下执行 | 子查询时会有多个 id |
| select_type | 查询类型：SIMPLE/PRIMARY/SUBQUERY/DERIVED | 出现 SUBQUERY/DERIVED 要警惕 |
| table | 访问的表名 | 多表 JOIN 会有多行 |
| type | **访问类型**（最重要） | 从好到差：system > const > eq_ref > ref > range > index > ALL |
| possible_keys | 可能用到的索引 | 为 NULL 说明没索引可用 |
| key | 实际选择的索引 | 为 NULL 说明没走索引 |
| key_len | 使用的索引长度 | 联合索引用了几列 |
| ref | 索引比较的值来源 | const 表示常量 |
| rows | **预估扫描行数** | 越小越好 |
| filtered | 过滤后剩余百分比 | 越高越好 |
| Extra | 附加信息 | Using filesort / Using temporary 需要优化 |

**type 列的值从好到差排列**：

- `const`：通过主键或唯一索引等值查询，最多返回一行，最快
- `eq_ref`：JOIN 时通过主键或唯一索引关联，一次只匹配一行
- `ref`：通过非唯一索引等值查询
- `range`：索引范围扫描（BETWEEN, >, <, IN）
- `index`：扫描整个索引树（比全表扫描好，但不理想）
- `ALL`：**全表扫描**（最差，必须优化）

**Extra 列中需要警惕的值**：

- `Using where`：在存储引擎返回数据后还需 Server 层过滤（常见，不一定有问题）
- `Using filesort`：**文件排序**，说明 ORDER BY 没有用到索引，需要额外排序操作
- `Using temporary`：**使用了临时表**，通常出现在 GROUP BY / DISTINCT / ORDER BY 场景
- `Using index`：**覆盖索引**，直接从索引获取数据，不需要回表，是理想状态
- `Using join buffer`：JOIN 时关联字段没有索引，使用了连接缓冲区

MySQL 还支持 `EXPLAIN ANALYZE`（8.0.18+），它会真正执行查询并显示实际耗时：

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 50000 AND status = 'paid';
```

输出示例：

```
-> Filter: (orders.status = 'paid')  (cost=3.46 rows=5) (actual time=0.123..0.456 rows=5 loops=1)
    -> Index lookup on orders using idx_user_id (user_id=50000)  (cost=3.46 rows=15) (actual time=0.089..0.234 rows=15 loops=1)
```

注意 `actual time` 和 `rows` 是真实值，`cost` 和 `rows`（不带 actual 的）是估算值。

#### PostgreSQL 的 EXPLAIN 输出

```sql
-- 同样的查询，PostgreSQL 版本
EXPLAIN SELECT * FROM orders WHERE user_id = 50000 AND status = 'paid';
```

PostgreSQL EXPLAIN 输出格式（树状缩进，从内层到外层）：

```
                               QUERY PLAN
------------------------------------------------------------------------
 Index Scan using idx_orders_user_id on orders  (cost=0.42..8.44 rows=1 width=148)
   Index Cond: (user_id = 50000)
   Filter: (status = 'paid'::text)
```

关键差异：

1. PostgreSQL 输出是缩进的树状结构，MySQL 是表格。树状结构在多表 JOIN 和子查询时更容易理解执行顺序。
2. PostgreSQL 默认显示 `cost`（成本估算）和 `width`（每行平均字节数），不显示 `rows` 的具体值（除非用 ANALYZE）。
3. PostgreSQL 的 `EXPLAIN ANALYZE` 会真正执行查询：

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 50000 AND status = 'paid';
```

```
                                                   QUERY PLAN
----------------------------------------------------------------------------------------------------------------
 Index Scan using idx_orders_user_id on orders  (cost=0.42..8.44 rows=1 width=148) (actual time=0.056..0.089 rows=5 loops=1)
   Index Cond: (user_id = 50000)
   Filter: (status = 'paid'::text)
   Rows Removed by Filter: 10
 Planning Time: 0.156 ms
 Execution Time: 0.112 ms
```

注意 PostgreSQL 的 EXPLAIN ANALYZE 输出多了几个重要信息：
- `actual time`：真实执行时间（毫秒）
- `rows`：真实返回行数
- `loops`：循环次数
- `Rows Removed by Filter`：被 Filter 条件过滤掉的行数
- `Planning Time`：生成执行计划的时间
- `Execution Time`：实际执行时间

PostgreSQL 还支持 `EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)` 来获取更详细的信息：

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 50000 AND status = 'paid';
```

```
 Index Scan using idx_orders_user_id on orders  (cost=0.42..8.44 rows=1 width=148) (actual time=0.056..0.089 rows=5 loops=1)
   Index Cond: (user_id = 50000)
   Filter: (status = 'paid'::text)
   Rows Removed by Filter: 10
   Buffers: shared hit=4 read=2
 Planning Time: 0.156 ms
 Execution Time: 0.112 ms
```

`Buffers: shared hit=4 read=2` 表示 4 个数据块从缓存命中，2 个从磁盘读取。这是 PostgreSQL 独有的 IO 级别统计。

#### 两者输出格式对比总结

| 对比维度 | MySQL | PostgreSQL |
|----------|-------|------------|
| 输出格式 | 表格（每行一个步骤） | 树状缩进（嵌套结构） |
| 成本估算 | rows 列（预估行数） | cost 范围（如 0.42..8.44） |
| 真实执行 | EXPLAIN ANALYZE (8.0.18+) | EXPLAIN ANALYZE（长期支持） |
| IO 统计 | 无直接对应 | BUFFERS 选项显示缓存命中 |
| 计划生成时间 | 无 | Planning Time |
| 可读性 | 需要理解列含义 | 缩进结构直观显示操作层次 |

### 11.1.2 慢查询定位

定位慢查询是性能优化的第一步。你不能凭猜测优化——需要让数据库告诉你"哪些查询慢"。

#### MySQL 慢查询日志

MySQL 的慢查询日志会记录所有执行时间超过阈值的查询。

```sql
-- 查看是否开启慢查询日志
SHOW VARIABLES LIKE 'slow_query_log';
-- 查看慢查询阈值（单位：秒）
SHOW VARIABLES LIKE 'long_query_time';
-- 查看日志文件位置
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 开启慢查询日志（运行时配置，重启后失效）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;  -- 超过 1 秒的查询记录到日志
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 永久配置需要修改 my.cnf（Windows 下为 my.ini）
-- [mysqld]
-- slow_query_log = 1
-- long_query_time = 1
-- slow_query_log_file = /var/log/mysql/slow.log
-- log_queries_not_using_indexes = 1  -- 记录不走索引的查询（即使很快）
```

配置好之后，慢查询日志文件内容类似：

```
# Time: 2024-01-15T10:23:45.123456Z
# User@Host: root[root] @ localhost [127.0.0.1]  Id: 123
# Query_time: 3.567890  Lock_time: 0.000123  Rows_sent: 20  Rows_examined: 1500000
SET timestamp=1705310625;
SELECT * FROM orders WHERE user_id = 50000 ORDER BY created_at DESC LIMIT 20;
```

关键字段解读：
- `Query_time`：查询总耗时（秒），这是你最关注的
- `Lock_time`：等待锁的时间，如果很高说明有锁竞争
- `Rows_sent`：返回给客户端的行数
- `Rows_examined`：**引擎层扫描的行数**——这个值远大于 Rows_sent 就说明有优化空间

MySQL 还提供了 `mysqldumpslow` 工具来汇总分析慢查询日志：

```bash
# 按总耗时排序，显示前 10 条
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log

# 按返回行数排序（找出扫描行数最多的查询）
mysqldumpslow -s r -t 10 /var/log/mysql/slow.log

# -s: 排序方式(t=按时间, r=按行数, c=按次数)
# -t: 显示前 N 条
# -g: 正则过滤
mysqldumpslow -s t -t 10 -g "orders" /var/log/mysql/slow.log
```

`mysqldumpslow` 会把具体的参数值替换成 `?`，把相同模式的查询聚合统计，方便你看出"哪类查询"最慢而不是"哪条具体的查询"。

#### PostgreSQL pg_stat_statements

PostgreSQL 的方案比 MySQL 更强大——它不记录原始 SQL 到文件，而是在内存中统计每类查询的执行次数、总耗时、平均耗时、最大耗时等聚合数据。

```sql
-- 1. 修改 postgresql.conf，加载扩展
-- shared_preload_libraries = 'pg_stat_statements'
-- pg_stat_statements.max = 10000
-- pg_stat_statements.track = all

-- 2. 重启 PostgreSQL 后，创建扩展
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- 3. 查询最慢的 10 条 SQL（按平均耗时排序）
SELECT
    query,                              -- SQL 文本（参数已归一化为 $1, $2）
    calls,                              -- 执行次数
    total_exec_time,                    -- 总执行时间（毫秒）
    mean_exec_time,                     -- 平均执行时间（毫秒）
    max_exec_time,                      -- 最大执行时间（毫秒）
    rows,                               -- 返回/影响的总行数
    shared_blks_hit,                    -- 缓存命中块数
    shared_blks_read,                   -- 磁盘读取块数
    100.0 * shared_blks_hit /
        NULLIF(shared_blks_hit + shared_blks_read, 0) AS cache_hit_ratio
FROM pg_stat_statements
WHERE query NOT ILIKE '%pg_stat_statements%'
ORDER BY mean_exec_time DESC
LIMIT 10;
```

输出示例：

```
           query            | calls | total_exec_time | mean_exec_time | max_exec_time | rows  | hit | read | hit_ratio
----------------------------+-------+-----------------+----------------+---------------+-------+-----+------+----------
 SELECT * FROM orders WHERE |  1542 |         8765.43 |          5.684 |         23.45 | 15420 | 800 |  200 |    80.0%
   user_id = $1 AND status  |       |                 |                |               |       |     |      |
   = $2 ORDER BY created_at |       |                 |                |               |       |     |      |
   DESC LIMIT $3            |       |                 |                |               |       |     |      |
```

`pg_stat_statements` 的优势在于：
1. 聚合统计——自动把相同模式的 SQL 归为一类，参数替换为 `$1, $2`
2. 持久化——统计数据在重启后依然保留（通过共享内存）
3. 全维度——不仅有执行时间，还有 IO 统计、行数统计、缓存命中率
4. 实时查询——直接用 SQL 查询统计视图，无需解析日志文件

```sql
-- 找出总耗时最高的 SQL（对系统整体影响最大的查询）
SELECT query, calls, total_exec_time,
       mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 找出缓存命中率低的查询（可能需要加索引或调优）
SELECT query, calls,
       shared_blks_hit, shared_blks_read,
       100.0 * shared_blks_hit /
           NULLIF(shared_blks_hit + shared_blks_read, 0) AS hit_pct
FROM pg_stat_statements
WHERE shared_blks_read > 0
ORDER BY shared_blks_read DESC
LIMIT 10;

-- 重置统计数据（重新开始统计）
SELECT pg_stat_statements_reset();
```

### 11.1.3 避免全表扫描：索引的正确使用

全表扫描（Full Table Scan）是性能杀手。当表数据量大时，全表扫描意味着数据库要逐行读取整张表的每一行数据来判断是否匹配 WHERE 条件。

前端类比：全表扫描就像你在一个 10000 条数据的数组里用 `Array.find()` 查找满足条件的元素——时间复杂度 O(n)。而索引扫描就像你在一个 Map 里用 `map.get(key)` 查找——时间复杂度 O(1) 或 O(log n)。B-Tree 索引就是数据库版的 Map/字典。

```sql
-- 反面案例：没有索引的查询
SELECT * FROM orders WHERE user_id = 50000;
-- 如果 user_id 上没有索引，数据库会扫描整张 orders 表

-- EXPLAIN 确认
EXPLAIN SELECT * FROM orders WHERE user_id = 50000;
-- type: ALL  <== 全表扫描，必须优化！

-- 解决方案：加索引
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 再看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = 50000;
-- type: ref, key: idx_orders_user_id  <== 走索引了
```

但索引不是万能的。在某些情况下即使有索引，数据库也可能选择不走索引：

```sql
-- 情况1：查询条件区分度太低
-- status 字段只有 'paid' 和 'unpaid' 两个值，且各占 50%
SELECT * FROM orders WHERE status = 'paid';
-- 优化器可能认为走索引扫描一半数据还不如直接全表扫描快
-- 这叫"索引选择性差"

-- 情况2：查询返回大部分数据
SELECT * FROM orders WHERE created_at > '2024-01-01';
-- 如果表中 80% 的数据都满足条件，走索引反而更慢
-- 因为索引扫描需要"回表"（先查索引拿主键，再查数据行）

-- 情况3：LIKE 前缀通配
SELECT * FROM orders WHERE order_no LIKE '%2024';
-- 前面有 % 通配符，B-Tree 索引无法使用
```

判断是否需要加索引的依据：

1. **该字段是否经常出现在 WHERE 条件中**——如果是，考虑加索引
2. **该字段是否经常用于 JOIN 关联**——如果是，必须加索引
3. **该字段是否经常用于 ORDER BY / GROUP BY**——如果是，考虑加索引
4. **该字段的区分度（选择性）是否足够高**——`选择性 = 不同值数量 / 总行数`，越高越好。性别字段的选择性约 0.5，不适合单独加索引；用户 ID 的选择性接近 1.0，非常适合加索引

### 11.1.4 LIMIT 深分页优化

这是后端开发中极其常见且容易被忽视的性能问题。

```sql
-- 第一页：很快
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 0;
-- MySQL 扫描 20 行，非常快

-- 第 1000 页：还行
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 20000;
-- MySQL 扫描 20020 行，丢弃前 20000 行，返回 20 行

-- 第 50000 页：很慢！
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000;
-- MySQL 扫描 1000020 行，丢弃前 1000000 行，返回 20 行
-- 偏移量越大，扫描的无效行数越多，性能急剧下降
```

前端类比：这就像前端用 `Array.slice(1000000, 1000020)` 从一个大数组取数据——虽然只取 20 条，但 JavaScript 引擎仍然需要遍历到第 1000000 个位置。数据库的 OFFSET 也是一样，它不是"跳过"，而是"扫描后丢弃"。

#### 优化方案一：延迟关联（Deferred Join）

核心思路：先用子查询只从索引中获取主键 ID，再通过主键 JOIN 回主表获取完整数据。减少回表次数。

```sql
-- 优化前：直接 LIMIT + OFFSET
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000;
-- 扫描 1000020 行数据行（含回表）

-- 优化后：延迟关联
SELECT t.* FROM orders t
INNER JOIN (
    SELECT id FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000
) tmp ON t.id = tmp.id;
-- 子查询中只扫描索引（覆盖索引，不回表），拿到 20 个 ID
-- 再用这 20 个 ID 去主表精确查找，只回表 20 次
```

如果 id 是主键，子查询 `SELECT id FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000` 会走主键索引的覆盖扫描（Using index），不需要回表。然后 JOIN 阶段只精确查找 20 行，大幅减少 IO。

#### 优化方案二：游标分页（Cursor-based Pagination / Keyset Pagination）

核心思路：记住上一页最后一条记录的某个有序字段值，下一页直接从该值之后开始查询，完全避免 OFFSET。

```sql
-- 第一页
SELECT * FROM orders ORDER BY id DESC LIMIT 20;
-- 假设第一页最后一条记录的 id = 1000001

-- 第二页：不用 OFFSET，直接用 WHERE 条件
SELECT * FROM orders WHERE id < 1000001 ORDER BY id DESC LIMIT 20;
-- 数据库只需要从 id=1000001 附近的索引位置开始，往后扫描 20 条即可
-- 不论翻到第几页，性能始终是 O(20)，不会随页码增大而变慢
```

游标分页的限制：只能"上一页/下一页"，不能直接跳转到第 N 页。但对于大多数业务场景（信息流、订单列表），用户通常是顺序翻页，游标分页是最佳选择。

前端类比：游标分页就像无限滚动的瀑布流页面——每次加载更多时，前端只需要告诉后端"最后一条记录的 ID"，后端就返回该 ID 之后的下一批数据。这正是 Twitter、Instagram 等应用使用的分页方案。

#### 优化方案三：覆盖索引

如果查询只需要索引中包含的列，数据库可以直接从索引返回数据，完全不需要回表。

```sql
-- 假设有一个联合索引 idx_user_status_created (user_id, status, created_at)

-- 优化前：需要回表
SELECT * FROM orders WHERE user_id = 50000 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;
-- 索引定位到匹配行后，还要回表取所有列（*）

-- 优化后：只查索引覆盖的列，不回表
SELECT id, user_id, status, created_at FROM orders
WHERE user_id = 50000 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;
-- Extra: Using index  <== 覆盖索引，完全不回表
```

#### Python 代码：游标分页的 FastAPI 实现

```python
"""
游标分页的 FastAPI 实现
适用于订单列表等无限滚动场景
"""
from fastapi import FastAPI, Query
from sqlalchemy import create_engine, text
from sqlalchemy.orm import sessionmaker
from typing import Optional
from pydantic import BaseModel

app = FastAPI()

# 数据库连接（MySQL 示例）
engine = create_engine(
    "mysql+pymysql://root:password@127.0.0.1:3306/shop?charset=utf8mb4",
    pool_size=10,
    max_overflow=20,
    pool_recycle=3600
)
Session = sessionmaker(bind=engine)


class OrderPage(BaseModel):
    items: list[dict]
    next_cursor: Optional[int]  # 下一页游标（最后一条记录的 id）
    has_more: bool


@app.get("/api/orders")
def list_orders(
    limit: int = Query(20, ge=1, le=100),
    cursor: Optional[int] = Query(None, description="上一页最后一条记录的 id")
):
    """
    游标分页 API
    - 第一页请求：GET /api/orders?limit=20（不传 cursor）
    - 下一页请求：GET /api/orders?limit=20&cursor=999980
    """
    session = Session()
    try:
        if cursor is not None:
            # 有游标：从游标之后开始查询
            sql = text("""
                SELECT id, user_id, status, amount, created_at
                FROM orders
                WHERE id < :cursor
                ORDER BY id DESC
                LIMIT :limit
            """)
            result = session.execute(sql, {"cursor": cursor, "limit": limit})
        else:
            # 无游标：第一页
            sql = text("""
                SELECT id, user_id, status, amount, created_at
                FROM orders
                ORDER BY id DESC
                LIMIT :limit
            """)
            result = session.execute(sql, {"limit": limit})

        rows = [dict(row._mapping) for row in result]

        # 计算下一页游标和是否还有更多数据
        has_more = len(rows) == limit
        next_cursor = rows[-1]["id"] if rows and has_more else None

        return OrderPage(
            items=rows,
            next_cursor=next_cursor,
            has_more=has_more
        )
    finally:
        session.close()
```

### 11.1.5 COUNT 优化：为什么 SELECT COUNT(*) 慢

```sql
-- 看似简单的查询，在大表上可能要好几秒
SELECT COUNT(*) FROM orders;
```

为什么 `COUNT(*)` 慢？因为 InnoDB（MySQL 默认存储引擎）的 MVCC 机制下，不同事务看到的数据版本不同，数据库无法维护一个精确的行计数器（MyISAM 可以因为它不支持事务）。所以 `COUNT(*)` 必须扫描整张表（或索引）来逐行计数。

PostgreSQL 的情况类似——也不维护精确计数，`COUNT(*)` 需要全表扫描。

#### 优化方案

```sql
-- 方案1：使用近似值（PostgreSQL 特有，速度极快）
-- pg_class.reltuples 存储了 ANALYZE 统计的近似行数
SELECT reltuples::bigint AS approx_count
FROM pg_class
WHERE relname = 'orders';
-- 结果近似但非常快（毫秒级），适合展示"大约有多少条数据"

-- MySQL 可以查 information_schema（但不太准确）
SELECT table_rows FROM information_schema.tables
WHERE table_schema = 'shop' AND table_name = 'orders';

-- 方案2：维护计数器表
CREATE TABLE row_counters (
    table_name  VARCHAR(100) PRIMARY KEY,
    row_count   BIGINT NOT NULL DEFAULT 0,
    updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 插入/删除数据时同步更新计数器
INSERT INTO row_counters (table_name, row_count) VALUES ('orders', 0)
ON CONFLICT (table_name)
DO UPDATE SET row_count = row_counters.row_count + 1,
              updated_at = CURRENT_TIMESTAMP;

-- 查询时直接查计数器表（O(1)）
SELECT row_count FROM row_counters WHERE table_name = 'orders';

-- 方案3：Redis 缓存计数
-- 对于需要实时更新的计数，用 Redis INCR/DECR
-- 定时任务同步到数据库
```

Python + Redis 计数方案：


### 11.1.6 子查询 vs JOIN 的性能选择

前端类比：子查询就像 JavaScript 中的嵌套函数调用——先执行内层函数得到结果，再传给外层函数处理。JOIN 就像 `Array.map()` 后再 `Array.flatMap()` 合并数据。在数据量大时，嵌套调用可能产生大量中间结果，而合并操作有时可以流式处理。

在大多数情况下，JOIN 比子查询性能更好，因为：
1. 子查询可能产生中间临时表
2. 相关子查询（Correlated Subquery）会对外层每一行重复执行内层查询
3. 优化器对 JOIN 的优化能力通常强于子查询

```sql
-- 场景：查询有未付款订单的用户信息

-- 方式1：相关子查询（EXISTS）
SELECT u.* FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id AND o.status = 'unpaid'
);
-- 对 users 表的每一行，都要执行一次子查询检查 orders 表

-- 方式2：IN 子查询
SELECT * FROM users
WHERE id IN (
    SELECT DISTINCT user_id FROM orders WHERE status = 'unpaid'
);
-- 先执行子查询获取所有未付款的 user_id，再在 users 表中匹配

-- 方式3：JOIN（推荐）
SELECT DISTINCT u.* FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE o.status = 'unpaid';
-- 优化器可以选择最优的 JOIN 顺序和策略

-- 方式4：PostgreSQL 的 EXCEPT / INTERSECT 替代方案
-- 查询没有未付款订单的用户
SELECT * FROM users
EXCEPT
SELECT u.* FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.status = 'unpaid';
```

但并非所有子查询都慢。MySQL 8.0+ 和 PostgreSQL 的优化器已经能将很多子查询自动改写为 JOIN。最佳实践是：

1. **简单等值条件用 IN**：对于少量结果通常没问题
2. **存在性检查用 EXISTS**：通常比 `IN` 更好（EXISTS 在找到第一个匹配后就返回）
3. **多表关联取数据用 JOIN**：需要从多张表获取字段时，JOIN 是最优选择
4. **用 EXPLAIN 验证**：不要猜，用 EXPLAIN 看执行计划

```sql
-- 验证：对比 IN 和 EXISTS 的执行计划
EXPLAIN SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE status = 'unpaid');
EXPLAIN SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.status = 'unpaid');
EXPLAIN SELECT DISTINCT u.* FROM users u JOIN orders o ON u.id = o.user_id WHERE o.status = 'unpaid';

-- 经验法则：子查询结果集小时用 IN，子查询结果集大时用 EXISTS 或 JOIN
```

## 11.2 索引优化

### 11.2.1 索引选择性分析

索引选择性（Selectivity）是衡量一个索引"好与不好"的核心指标。选择性越高，索引越有效。

**选择性 = 该列不同值的数量 / 该表总行数**

```sql
-- 计算各列的选择性
SELECT
    COUNT(*) AS total_rows,
    COUNT(DISTINCT user_id) AS distinct_user,
    COUNT(DISTINCT status) AS distinct_status,
    COUNT(DISTINCT order_no) AS distinct_order_no,
    ROUND(COUNT(DISTINCT user_id) / COUNT(*), 4) AS user_id_selectivity,
    ROUND(COUNT(DISTINCT status) / COUNT(*), 4) AS status_selectivity,
    ROUND(COUNT(DISTINCT order_no) / COUNT(*), 4) AS order_no_selectivity
FROM orders;
```

结果示例：

```
total_rows | distinct_user | distinct_status | distinct_order_no | user_id_sel | status_sel | order_no_sel
-----------+---------------+-----------------+-------------------+-------------+------------+-------------
   1000000 |        100000 |               3 |           1000000 |      0.1000 |     0.0000 |       1.0000
```

解读：
- `order_no`（订单号）选择性 = 1.0，每个值都不同，非常适合加索引
- `user_id`（用户ID）选择性 = 0.1，10 万个不同值，适合加索引
- `status`（状态）选择性 = 0.000003，只有 3 个不同值，**不该单独加索引**

为什么低选择性的字段不该加索引？因为数据库优化器会判断：如果通过索引要访问超过 20%-30% 的行，不如直接全表扫描更快（索引扫描需要"回表"，随机 IO 比全表扫描的顺序 IO 更慢）。

前端类比：如果你有一个 1000 个元素的数组，你要找出所有 `type === 'A'` 的元素。如果 type 只有两种值各占 50%，你直接遍历一遍（全表扫描）比维护一个"类型索引"再查找更快。但如果你要找 `id === 12345`，用 Map 查找（索引查找）快得多。

### 11.2.2 联合索引顺序设计

联合索引（Composite Index）的列顺序至关重要。B-Tree 索引遵循"最左前缀原则"——只有从最左列开始连续匹配的列才能用到索引。

```sql
-- 假设有一个联合索引 idx_a_b_c (a, b, c)
CREATE INDEX idx_a_b_c ON orders(a, b, c);

-- 能用到索引的查询：
SELECT * FROM orders WHERE a = 1;                         -- 用到 a
SELECT * FROM orders WHERE a = 1 AND b = 2;              -- 用到 a, b
SELECT * FROM orders WHERE a = 1 AND b = 2 AND c = 3;   -- 用到 a, b, c
SELECT * FROM orders WHERE a = 1 AND c = 3;              -- 只用到 a（c 用不到，因为 b 断了）

-- 用不到索引的查询：
SELECT * FROM orders WHERE b = 2;                         -- 不从 a 开始，用不到
SELECT * FROM orders WHERE b = 2 AND c = 3;              -- 同上
SELECT * FROM orders WHERE c = 3;                         -- 同上
```

联合索引设计原则：

1. **等值查询在前，范围查询在后**：如果查询有 `a = 1 AND b > 5`，索引应设计为 `(a, b)` 而非 `(b, a)`，因为范围查询之后的列无法用到索引
2. **高选择性在前**：区分度高的列放前面，能更快缩小扫描范围
3. **覆盖索引考量**：如果查询只需要索引中的列，可以把所有需要的列都放入联合索引

```sql
-- 实战案例：订单查询场景
-- 常见查询模式：
-- 1. WHERE user_id = ? AND status = ? ORDER BY created_at DESC
-- 2. WHERE user_id = ? ORDER BY created_at DESC
-- 3. WHERE user_id = ? AND created_at > ?

-- 联合索引设计：(user_id, status, created_at)
CREATE INDEX idx_orders_user_status_created ON orders(user_id, status, created_at);

-- 查询1：完美匹配，三列全部用到，且 ORDER BY 也用到索引
EXPLAIN SELECT * FROM orders
WHERE user_id = 50000 AND status = 'paid'
ORDER BY created_at DESC;
-- type: ref, key: idx_orders_user_status_created, Extra: NULL（不需要 filesort）

-- 查询2：用到 user_id 和 created_at（跳过 status，但 created_at 用于 ORDER BY）
EXPLAIN SELECT * FROM orders
WHERE user_id = 50000
ORDER BY created_at DESC;
-- 仍然能用到索引（user_id 等值匹配 + created_at 排序）

-- 查询3：用到 user_id 等值 + created_at 范围
EXPLAIN SELECT * FROM orders
WHERE user_id = 50000 AND created_at > '2024-01-01'
ORDER BY created_at DESC;
-- user_id 等值匹配，created_at 范围扫描 + 排序，都能用到索引
```

### 11.2.3 索引失效场景

这是实际开发中最容易踩坑的地方——你加了索引，但查询却没走索引。以下列举常见的索引失效场景。

#### 场景一：对索引列使用函数

```sql
-- 反面案例：在索引列上使用函数
CREATE INDEX idx_orders_created ON orders(created_at);

SELECT * FROM orders WHERE DATE(created_at) = '2024-01-15';
-- 索引失效！因为 DATE() 函数改变了列的值，B-Tree 索引无法匹配

-- 正确写法：改用范围查询
SELECT * FROM orders
WHERE created_at >= '2024-01-15 00:00:00'
  AND created_at <  '2024-01-16 00:00:00';
-- 索引有效！范围查询直接在索引树上比较

-- MySQL 的另一种方案：函数索引（MySQL 8.0+）
CREATE INDEX idx_orders_created_date ON orders((DATE(created_at)));

-- PostgreSQL 的方案：表达式索引
CREATE INDEX idx_orders_created_date ON orders((created_at::date));
SELECT * FROM orders WHERE created_at::date = '2024-01-15';  -- 走索引
```

#### 场景二：类型隐式转换

```sql
-- 反面案例：字符串字段与数字比较（MySQL 中索引失效）
CREATE INDEX idx_orders_order_no ON orders(order_no);  -- order_no 是 VARCHAR

SELECT * FROM orders WHERE order_no = 202401150001;  -- 传了数字，不是字符串
-- MySQL 会把 order_no 转换成数字再比较，导致索引失效

-- 正确写法：传入正确类型的字符串
SELECT * FROM orders WHERE order_no = '202401150001';
-- 索引有效！

-- PostgreSQL 的情况：会直接报类型错误，更加严格
-- SELECT * FROM orders WHERE order_no = 202401150001;
-- ERROR: operator does not exist: varchar = integer
```

前端类比：这就像 JavaScript 中的 `==` 和 `===` 的区别。`0 == "0"` 会触发隐式类型转换。数据库也有类似行为，MySQL 在比较不同类型时会做隐式转换，而隐式转换可能让索引失效。PostgreSQL 更严格，类型不匹配直接报错，反而避免了这种隐蔽的 bug。

#### 场景三：OR 条件导致索引失效

```sql
-- 反面案例：OR 连接两个不同字段的查询
SELECT * FROM orders WHERE user_id = 50000 OR status = 'paid';
-- 如果 user_id 有索引但 status 没有索引，MySQL 可能放弃使用索引

-- 方案1：用 UNION ALL 改写
SELECT * FROM orders WHERE user_id = 50000
UNION ALL
SELECT * FROM orders WHERE status = 'paid' AND user_id != 50000;
-- 每个子查询可以独立使用各自的索引

-- 方案2：为两个字段都加索引，MySQL 可能使用 Index Merge（8.0+）
CREATE INDEX idx_orders_status ON orders(status);
SELECT * FROM orders WHERE user_id = 50000 OR status = 'paid';
-- MySQL 可能使用 index_merge 优化，合并两个索引的结果
```

#### 场景四：LIKE 前缀通配

```sql
-- 反面案例：LIKE 以 % 开头
SELECT * FROM orders WHERE order_no LIKE '%2024';
-- 索引失效！B-Tree 索引是按从左到右排序的，前缀通配符无法确定起始位置

-- 正确写法：LIKE 以具体字符开头
SELECT * FROM orders WHERE order_no LIKE '2024%';
-- 索引有效！'2024%' 可以在 B-Tree 上做范围扫描

-- 如果必须使用前缀通配搜索：
-- MySQL: 使用全文索引
ALTER TABLE orders ADD FULLTEXT INDEX ft_order_no(order_no);
SELECT * FROM orders WHERE MATCH(order_no) AGAINST('2024' IN NATURAL LANGUAGE MODE);

-- PostgreSQL: 使用 pg_trgm 扩展
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_orders_order_no_trgm ON orders USING gin (order_no gin_trgm_ops);
SELECT * FROM orders WHERE order_no LIKE '%2024%';  -- 现在能走 GIN 索引
```

### 11.2.4 前缀索引（MySQL）：长字符串字段的索引优化

当字段是很长的字符串（如 URL、UUID、长文本），直接对整个字段建索引会浪费大量存储空间，且索引树变大导致查询变慢。前缀索引只对字符串的前 N 个字符建索引。

```sql
-- 计算前缀长度选择性的方法：找到选择性接近 1.0 的最短前缀长度
SELECT
    COUNT(DISTINCT LEFT(url, 5)) / COUNT(*) AS sel_5,
    COUNT(DISTINCT LEFT(url, 10)) / COUNT(*) AS sel_10,
    COUNT(DISTINCT LEFT(url, 15)) / COUNT(*) AS sel_15,
    COUNT(DISTINCT LEFT(url, 20)) / COUNT(*) AS sel_20,
    COUNT(DISTINCT LEFT(url, 30)) / COUNT(*) AS sel_30
FROM urls;
-- 假设输出：sel_5=0.2, sel_10=0.85, sel_15=0.99, sel_20=1.0
-- 选择 15 作为前缀长度：选择性已达 0.99，够用

-- 创建前缀索引
ALTER TABLE urls ADD INDEX idx_url_prefix(url(15));

-- 查询时
SELECT * FROM urls WHERE url = 'https://www.example.com/path/to/page';
-- 前缀索引能帮助快速定位到匹配前缀的行，然后回表验证完整 URL
```

前缀索引的局限：
1. **不能用于覆盖索引**——因为索引中只存了前缀，无法完整返回字段值
2. **不能用于 ORDER BY**——前缀排序不等于完整值排序
3. **不能用于 GROUP BY**——同上

PostgreSQL 没有直接的前缀索引语法，但可以用表达式索引达到类似效果：

```sql
-- PostgreSQL 表达式索引：对前 N 个字符建索引
CREATE INDEX idx_url_prefix ON urls (left(url, 15));
SELECT * FROM urls WHERE left(url, 15) = left('https://www.example.com/path/to/page', 15);
-- 注意：查询时也需要使用相同的表达式才能走索引
```

### 11.2.5 PostgreSQL 的表达式索引和部分索引

PostgreSQL 在索引方面比 MySQL 更灵活，支持两种 MySQL 不直接支持（或支持有限）的索引类型。

#### 表达式索引（Expression Index）

可以对表达式或函数调用的结果建索引，而不仅仅是列本身。

```sql
-- 场景：经常需要按用户邮箱域名查询
CREATE INDEX idx_users_email_domain ON users (split_part(email, '@', 2));
SELECT * FROM users WHERE split_part(email, '@', 2) = 'gmail.com';  -- 走索引

-- 另一个场景：大小写不敏感查询
CREATE INDEX idx_users_name_lower ON users (lower(name));
SELECT * FROM users WHERE lower(name) = 'zhang san';  -- 走索引
```

#### 部分索引（Partial Index）

只对满足特定条件的行建索引，而非全表所有行。适用于"大部分数据不查询，只有一小部分需要查询"的场景。

```sql
-- 场景：订单表有 1000 万行，但只有 5% 是"待处理"状态
-- 而待处理订单是查询最频繁的

-- 部分索引：只索引"待处理"的行
CREATE INDEX idx_orders_pending ON orders(id) WHERE status = 'pending';
-- 索引只包含约 50 万行，体积小，写入开销小

-- 查询时自动使用部分索引
SELECT * FROM orders WHERE status = 'pending' AND id > 100;
-- 优化器发现 WHERE 条件满足部分索引的条件，使用 idx_orders_pending

-- 另一个场景：只对活跃用户建索引
CREATE INDEX idx_users_active ON users(last_login_at)
WHERE status = 'active' AND last_login_at IS NOT NULL;
-- 只为活跃且有登录记录的用户建索引，减少索引体积
```

部分索引的优势：
1. 索引体积更小——节省存储空间，提高缓存命中率
2. 写入更快——不需要为不满足条件的行维护索引
3. 查询更快——在有效索引中扫描的数据量更小

### 11.2.6 索引维护：重建索引、碎片整理

索引在长期使用（大量 INSERT/UPDATE/DELETE）后会产生碎片，导致索引树不平衡、查询效率下降。

#### MySQL 索引维护

```sql
-- 重建表（包括所有索引）：MySQL 推荐方式
ALTER TABLE orders ENGINE=InnoDB;
-- 或使用 OPTIMIZE TABLE（等价于重建+分析）
OPTIMIZE TABLE orders;

-- 分析表统计信息（让优化器重新统计索引分布）
ANALYZE TABLE orders;

-- 查看索引碎片情况
SELECT
    table_name,
    data_free / 1024 / 1024 AS free_mb,  -- 碎片空间（MB）
    data_length / 1024 / 1024 AS data_mb  -- 数据空间（MB）
FROM information_schema.tables
WHERE table_schema = 'shop' AND table_name = 'orders';
-- 如果 free_mb 接近或超过 data_mb 的 20%，建议重建
```

#### PostgreSQL 索引维护

```sql
-- 重建单个索引
REINDEX INDEX idx_orders_user_id;

-- 重建整张表的所有索引
REINDEX TABLE orders;

-- 并行重建索引（PostgreSQL 12+，利用多核加速）
REINDEX INDEX CONCURRENTLY idx_orders_user_id;
-- CONCURRENTLY：不锁表，允许并发读写，但耗时更长

-- 更新统计信息
ANALYZE orders;

-- 查看索引健康度
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan AS index_scans,        -- 索引被使用的次数
    idx_tup_read,                    -- 从索引读取的行数
    idx_tup_fetch                    -- 通过索引获取的行数（回表）
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY idx_scan;
-- idx_scan 为 0 的索引可能从未被使用过，考虑删除
```

定期维护的建议：
- 生产环境高峰期不要做 REINDEX（可能锁表）
- CONCURRENTLY 模式适合生产环境但耗时更长
- 定期执行 ANALYZE 更新统计信息（推荐每天或每周一次）
- 监控从未使用的索引（idx_scan = 0）并清理

## 11.3 表结构优化

### 11.3.1 合理的反范式：适当冗余减少 JOIN

范式设计（Normalization）的核心是"消除冗余"——一个数据只在一个地方存储。但这在查询时会导致大量 JOIN 操作。反范式（Denormalization）则是有意引入冗余，以空间换时间。

前端类比：范式设计就像你把数据拆成多个独立的模块，需要时再组合（类似 Redux 的 normalized state）。反范式就像你提前把组合好的数据缓存一份（类似 React 的 useMemo）——虽然多占内存，但渲染时不用重新计算。

```sql
-- 范式设计：需要 4 张表 JOIN 才能获取完整订单信息
SELECT
    o.id, o.order_no, o.amount, o.created_at,
    u.username,
    p.name AS product_name,
    c.name AS category_name
FROM orders o
INNER JOIN users u ON o.user_id = u.id
INNER JOIN products p ON o.product_id = p.id
INNER JOIN categories c ON p.category_id = c.id
WHERE o.status = 'paid'
ORDER BY o.created_at DESC
LIMIT 20;
-- 4 表 JOIN 在大数据量下可能很慢

-- 反范式设计：在 orders 表中冗余存储用户名和商品名
ALTER TABLE orders ADD COLUMN username VARCHAR(50);
ALTER TABLE orders ADD COLUMN product_name VARCHAR(200);
ALTER TABLE orders ADD COLUMN category_name VARCHAR(100);

-- 查询时不需要 JOIN
SELECT id, order_no, amount, created_at,
       username, product_name, category_name
FROM orders
WHERE status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
-- 单表查询，性能大幅提升

-- 但冗余带来一致性问题：用户改名后 orders 表中的 username 就过时了
-- 解决方案：1. 不需要实时同步的场景（历史订单快照）不更新
--          2. 需要同步的场景通过异步消息队列更新
--          3. 使用触发器自动更新（但增加写入开销）
```

**反范式的适用场景**：

1. **历史快照数据**：订单记录的是下单时的商品名和价格，即使后来商品改名或改价也不影响历史订单——这时的冗余不是冗余，而是业务需要
2. **读多写少的场景**：如果某个 JOIN 查询每天执行上万次，但关联数据一周才改一次，冗余存储能极大提升读取性能
3. **统计报表场景**：预计算并冗余存储汇总数据，避免每次实时计算

```sql
-- 反范式案例：商品表冗余存储统计数据
ALTER TABLE products ADD COLUMN sales_count INT DEFAULT 0;
ALTER TABLE products ADD COLUMN avg_rating DECIMAL(3,2) DEFAULT 0;
ALTER TABLE products ADD COLUMN review_count INT DEFAULT 0;

-- 触发器自动维护统计（PostgreSQL）
CREATE OR REPLACE FUNCTION update_product_stats()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE products
        SET sales_count = sales_count + 1
        WHERE id = NEW.product_id;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_sales_count
AFTER INSERT ON orders
FOR EACH ROW EXECUTE FUNCTION update_product_stats();
```

### 11.3.2 大表拆分：垂直拆分与水平拆分

当单表数据量达到千万级甚至亿级，即使索引优化到极致也可能遇到瓶颈。这时需要考虑拆分。

#### 垂直拆分（Vertical Partitioning）：拆字段

将一张宽表的列拆分到多张表中。通常按"访问频率"和"字段大小"来拆。

```sql
-- 垂直拆分后：按访问频率和字段大小拆分
-- 表1：高频访问的基础信息（小字段）
CREATE TABLE users_base (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(255),
    status SMALLINT DEFAULT 1,
    last_login_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ
);

-- 表2：低频访问的大字段
CREATE TABLE users_profile (
    user_id BIGINT PRIMARY KEY REFERENCES users_base(id),
    avatar_url VARCHAR(500),
    bio TEXT,
    preferences JSONB
);
```

前端类比：垂直拆分就像你把一个巨大的 React 组件拆分成多个小组件。原来一个大组件渲染所有内容，现在拆成 `<UserBasic>` 和 `<UserProfile>`，需要哪个渲染哪个。

#### 水平拆分（Horizontal Partitioning/Sharding）：拆行

将同一张表的不同行分散到多张表（甚至多个数据库实例）中。

```python
"""
按 user_id 取模分表的路由
"""
from sqlalchemy import text

class OrderSharding:
    TABLE_COUNT = 8

    @classmethod
    def get_table_name(cls, user_id: int) -> str:
        return f"orders_{user_id % cls.TABLE_COUNT}"

    @classmethod
    def get_order(cls, session, user_id: int, order_id: int):
        table = cls.get_table_name(user_id)
        sql = text(f"SELECT * FROM {table} WHERE id = :oid AND user_id = :uid")
        result = session.execute(sql, {"oid": order_id, "uid": user_id})
        return result.fetchone()
```

水平拆分的复杂点：
1. **跨分片查询**：查询不包含分片键时，需要扫描所有分片再合并结果
2. **跨分片 JOIN**：两张分片表 JOIN 几乎不可能，通常需要在应用层处理
3. **分布式事务**：跨分片的写操作需要分布式事务保证一致性
4. **全局唯一 ID**：不能再用自增 ID，需要雪花 ID 或 UUID
5. **扩容困难**：从 8 个分片扩到 16 个分片需要重新分配数据

因此水平拆分通常是"最后手段"——在索引优化、分区表、读写分离都尝试过后仍然不够时才考虑。

### 11.3.3 历史数据归档：冷热数据分离

生产环境中，大部分查询只访问最近的数据（热数据），历史数据（冷数据）很少被查询但占据了表的大部分空间。将冷数据归档到单独的表，能让热表保持较小体积，查询更快。

```sql
-- 场景：orders 表有 5000 万行，其中 4500 万行是一年前的历史数据

-- 方案1：创建历史归档表
CREATE TABLE orders_archive (LIKE orders INCLUDING ALL);

-- 定时归档
BEGIN;
INSERT INTO orders_archive
SELECT * FROM orders WHERE created_at < NOW() - INTERVAL '3 months';
DELETE FROM orders WHERE created_at < NOW() - INTERVAL '3 months';
COMMIT;

-- 归档后，orders 表从 5000 万行降到 500 万行

-- 方案2：使用分区表自动管理冷热数据（推荐，见下节）
```

### 11.3.4 分区表设计

分区表（Partitioning）是数据库原生支持的"水平拆分"方案。与应用层分表不同，分区表在数据库内部完成，对应用透明——查询时仍然使用一张表名，数据库自动路由到对应分区。

#### MySQL 分区表

```sql
-- MySQL 8.0 RANGE 分区：按时间范围
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT,
    order_no VARCHAR(50),
    user_id BIGINT,
    amount DECIMAL(12,2),
    status VARCHAR(20),
    created_at DATETIME NOT NULL,
    PRIMARY KEY (id, created_at)  -- 分区键必须是主键的一部分
)
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p202401 VALUES LESS THAN (TO_DAYS('2024-02-01')),
    PARTITION p202402 VALUES LESS THAN (TO_DAYS('2024-03-01')),
    PARTITION p202403 VALUES LESS THAN (TO_DAYS('2024-04-01')),
    PARTITION pmax VALUES LESS THAN MAXVALUE
);

-- 查询时自动分区裁剪（Partition Pruning）
SELECT * FROM orders WHERE created_at >= '2024-03-01' AND created_at < '2024-04-01';
-- 只扫描 p202403 分区，不扫描其他分区

-- LIST 分区：按离散值分区
CREATE TABLE orders_by_region (
    id BIGINT AUTO_INCREMENT,
    region VARCHAR(20),
    amount DECIMAL(12,2),
    PRIMARY KEY (id, region)
)
PARTITION BY LIST COLUMNS(region) (
    PARTITION p_east VALUES IN ('shanghai', 'beijing', 'tianjin'),
    PARTITION p_south VALUES IN ('guangzhou', 'shenzhen', 'xiamen'),
    PARTITION p_west VALUES IN ('chengdu', 'xian', 'kunming')
);

-- HASH 分区：按哈希值均匀分布
CREATE TABLE orders_hash (
    id BIGINT AUTO_INCREMENT,
    user_id BIGINT,
    amount DECIMAL(12,2),
    PRIMARY KEY (id, user_id)
)
PARTITION BY HASH(user_id)
PARTITIONS 8;

-- 删除旧分区（高效归档：直接删除整个分区文件，比 DELETE 快得多）
ALTER TABLE orders DROP PARTITION p202401;
```

#### PostgreSQL 分区表

```sql
-- PostgreSQL 声明式分区（PG 10+）
CREATE TABLE orders (
    id BIGSERIAL,
    order_no VARCHAR(50),
    user_id BIGINT,
    amount DECIMAL(12,2),
    status VARCHAR(20),
    created_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 创建子分区
CREATE TABLE orders_202401 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE orders_202402 PARTITION OF orders
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
CREATE TABLE orders_default PARTITION OF orders DEFAULT;

-- 配合 pg_partman 扩展实现自动创建未来分区
CREATE EXTENSION IF NOT EXISTS pg_partman;
SELECT partman.create_parent('public.orders', 'created_at', 'native', 'monthly');

-- LIST 分区
CREATE TABLE orders_by_region (
    id BIGSERIAL,
    region VARCHAR(20),
    amount DECIMAL(12,2),
    PRIMARY KEY (id, region)
) PARTITION BY LIST (region);

CREATE TABLE orders_east PARTITION OF orders_by_region
    FOR VALUES IN ('shanghai', 'beijing', 'tianjin');

-- HASH 分区
CREATE TABLE orders_hash (
    id BIGSERIAL,
    user_id BIGINT,
    amount DECIMAL(12,2)

CREATE TABLE orders_hash_0 PARTITION OF orders_hash FOR VALUES WITH (modulus 8, remainder 0);

-- 删除旧分区（极快，直接删除文件）
DROP TABLE orders_202401;
-- 或将旧分区分离出来
ALTER TABLE orders DETACH PARTITION orders_202401;
```

### 11.3.5 JSONB 字段的使用与索引优化

JSONB（PostgreSQL）和 JSON（MySQL 8.0+）允许在关系型数据库中存储半结构化数据。但 JSON 字段的查询性能需要特别关注索引设计。

#### PostgreSQL JSONB 索引优化

```sql
-- GIN 索引：支持所有 JSONB 操作符（@>, ?, ?|, ?&）
CREATE INDEX idx_products_attr_gin ON products USING gin (attributes);
SELECT * FROM products WHERE attributes @> '{"color": "red"}';

-- B-Tree 表达式索引：只对某个 JSONB 键建索引（更省空间）
CREATE INDEX idx_products_color ON products ((attributes->>'color'));
SELECT * FROM products WHERE attributes->>'color' = 'red';

-- 多键表达式索引
CREATE INDEX idx_products_color_size ON products
    ((attributes->>'color'), (attributes->>'size'));

-- JSONB 路径索引（针对嵌套 JSON）
-- 场景：{"specs": {"cpu": "i7", "ram": "16GB"}}
CREATE INDEX idx_products_cpu ON products ((attributes#>>'{specs,cpu}'));
SELECT * FROM products WHERE attributes#>>'{specs,cpu}' = 'i7';
```

#### MySQL JSON 索引优化

```sql
-- 方案1：生成列 + 索引（MySQL 5.7+）
ALTER TABLE products
ADD COLUMN color VARCHAR(50)
    GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(attributes, '$.color'))) STORED;

CREATE INDEX idx_products_color ON products(color);
SELECT * FROM products WHERE attributes->>'$.color' = 'red';

-- 方案2：MySQL 8.0.17+ 多值索引（Multi-Valued Index）
-- 适用于 JSON 数组字段
ALTER TABLE products
ADD COLUMN tags JSON GENERATED ALWAYS AS (attributes->'$.tags') VIRTUAL;

CREATE INDEX idx_products_tags ON products((CAST(tags AS CHAR(255) ARRAY)));
SELECT * FROM products WHERE 'sports' MEMBER OF (attributes->'$.tags');
```

## 11.4 连接池与并发优化

### 11.4.1 连接池配置原理

数据库连接是昂贵的资源——每次建立 TCP 连接、认证握手、分配内存缓冲区的开销都不小。在高并发场景下，如果每个请求都新建连接再关闭，数据库会被连接建立/断开的开销拖垮。

前端类比：连接池就像前端的 HTTP 连接复用（Keep-Alive）。如果没有连接复用，每次 `fetch` 请求都要新建 TCP 连接、TLS 握手，延迟很高。连接池就是让多个请求复用已建立的数据库连接。

连接池的核心参数：

| 参数 | 含义 | 配置建议 |
|------|------|----------|
| pool_size | 最小连接数（保持的常驻连接） | 根据日常 QPS 设定，通常 5-20 |
| max_overflow | 最大溢出连接数 | 根据峰值流量设定，通常 10-30 |
| pool_timeout | 等待空闲连接的超时时间 | 30 秒，超时报错 |
| pool_recycle | 连接最大存活时间 | 3600 秒，防止被数据库主动断开 |
| pool_pre_ping | 使用前检查连接是否有效 | True，防止使用已断开的连接 |

### 11.4.2 MySQL 连接池：SQLAlchemy Pool（Python）

```python
"""
SQLAlchemy 连接池配置（MySQL）
"""
from sqlalchemy import create_engine
from sqlalchemy.pool import QueuePool

# 基本连接池配置
engine = create_engine(
    "mysql+pymysql://root:password@127.0.0.1:3306/shop?charset=utf8mb4",
    poolclass=QueuePool,
    pool_size=10,           # 常驻连接数
    max_overflow=20,       # 最大溢出连接数（总连接数上限 = 30）
    pool_timeout=30,       # 等待连接超时（秒）
    pool_recycle=3600,     # 连接回收时间（秒）
    pool_pre_ping=True,    # 使用前 ping 检查连接有效性
)

# 生产环境推荐配置
def create_production_engine():
    return create_engine(
        "mysql+pymysql://user:password@db-host:3306/shop?charset=utf8mb4",
        pool_size=20,
        max_overflow=30,
        pool_timeout=10,      # 10 秒等不到连接就报错（快速失败）
        pool_recycle=1800,    # 30 分钟回收连接
        pool_pre_ping=True,
        echo=False,
    )

# 异步 SQLAlchemy
from sqlalchemy.ext.asyncio import create_async_engine

async_engine = create_async_engine(
    "mysql+asyncmy://root:password@127.0.0.1:3306/shop?charset=utf8mb4",
    pool_size=10,
    max_overflow=20,
    pool_timeout=30,
    pool_recycle=3600,
    pool_pre_ping=True,
)

# 监控连接池状态
def check_pool_status():
    pool = engine.pool
    print(f"Pool size: {pool.size()}")
    print(f"Checked out: {pool.checkedout()}")
    print(f"Checked in: {pool.checkedin()}")
    print(f"Overflow: {pool.overflow()}")
```

### 11.4.3 PostgreSQL 连接池：PgBouncer 的使用

PostgreSQL 的进程模型中，每个连接对应一个后端进程（fork 进程），连接数过多会导致进程数爆炸、内存消耗大。因此 PostgreSQL 比 MySQL 更需要专业的连接池中间件。

```
应用层（1000 个连接）
    |
    v
PgBouncer（连接池，100 个后端连接）
    |
    v
PostgreSQL（100 个后端进程）
```

PgBouncer 配置文件（pgbouncer.ini）：

```ini
;; PgBouncer 配置文件
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop user=app_user password=secret

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432

;; 连接池模式：session / transaction / statement
pool_mode = transaction
;; session:  一个客户端连接绑定一个后端连接（连接复用度低）
;; transaction: 事务级别复用（推荐，一个事务用完连接就归还池中）
;; statement: 语句级别复用（不支持事务，复用度最高但功能受限）

max_client_conn = 1000      ; 客户端最大连接数
default_pool_size = 25      ; 每个数据库/用户的后端连接数
min_pool_size = 5           ; 最小空闲后端连接
reserve_pool_size = 5       ; 预留连接数
reserve_pool_timeout = 3    ; 等待预留连接的超时（秒）

server_idle_timeout = 300   ; 后端连接空闲超时（秒）
query_wait_timeout = 30     ; 客户端等待连接的超时（秒）

log_connections = 1
log_disconnections = 1
log_pooler_errors = 1
admin_users = pgbouncer_admin
```

Python 连接 PgBouncer：

```python
注意端口从 5432 改为 6432
```

### 11.4.4 长事务的危害与排查

长事务（Long Running Transaction）是连接池和数据库性能的隐形杀手。一个事务持有连接和锁的时间过长，会阻塞其他事务，导致连接耗尽和锁等待。

```sql
-- MySQL：查看当前运行的事务
SELECT
    trx_id,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_seconds,
    trx_state,
    trx_query,
    trx_mysql_thread_id
FROM information_schema.innodb_trx
ORDER BY trx_started ASC
LIMIT 10;
-- duration_seconds 超过 60 秒的事务需要重点排查

-- PostgreSQL：查看长事务
SELECT
    pid,
    usename,
    state,
    query,
    now() - xact_start AS transaction_duration,
    now() - query_start AS query_duration,
    waiting
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY xact_start ASC;

-- 强制终止长事务（谨慎操作！）
-- MySQL: KILL <thread_id>;
-- PostgreSQL: SELECT pg_terminate_backend(<pid>);
```

长事务的常见原因和预防：

```python
# 反面案例：在事务中做耗时操作（HTTP 请求、文件 IO 等）
def bad_transaction_example(session, user_id):
    """危险：事务中包含网络请求"""
    try:
        session.begin()
        user = session.execute(
            text("SELECT * FROM users WHERE id = :id"), {"id": user_id}
        ).fetchone()

        # 在事务中调用外部 API（可能耗时数秒甚至超时）
        # 这会导致数据库连接和锁被长时间持有！
        response = httpx.post("https://api.payment.com/charge", json={"amount": 100})
        if response.status_code != 200:
            raise Exception("Payment failed")

        session.execute(
            text("UPDATE orders SET status = 'paid' WHERE user_id = :id"),
            {"id": user_id}
        )
        session.commit()
    except Exception:
        session.rollback()
        raise

# 正确做法：将耗时操作移到事务外
def good_transaction_example(session, user_id):
    """正确：先做网络请求，再开事务"""
    try:
        # 先在事务外做网络请求
        response = httpx.post("https://api.payment.com/charge", json={"amount": 100})
        if response.status_code != 200:
            raise Exception("Payment failed")

        # 网络请求成功后，再快速完成数据库事务
        session.begin()
        session.execute(
            text("UPDATE orders SET status = 'paid' WHERE user_id = :id"),
            {"id": user_id}
        )
        session.commit()  # 事务持续时间极短
    except Exception:
        session.rollback()
        raise
```

### 11.4.5 连接数耗尽的排查与解决

当应用报错 "Too many connections"（MySQL）或 "FATAL: sorry, too many clients already"（PostgreSQL），说明数据库连接数已耗尽。

```sql
-- MySQL：查看连接使用情况
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Max_used_connections';

-- 查看各客户端的连接数分布
SELECT
    host,
    user,
    COUNT(*) AS connection_count,
    SUM(CASE WHEN command = 'Sleep' THEN 1 ELSE 0 END) AS idle_count,
    SUM(CASE WHEN command != 'Sleep' THEN 1 ELSE 0 END) AS active_count
FROM information_schema.processlist
GROUP BY host, user
ORDER BY connection_count DESC;

-- PostgreSQL：查看连接数
SHOW max_connections;
SELECT count(*) FROM pg_stat_activity;
SELECT count(*) FROM pg_stat_activity WHERE state = 'active';
SELECT count(*) FROM pg_stat_activity WHERE state = 'idle';
```

连接泄漏的排查（Python）：

```python
"""
连接泄漏的常见原因：忘记关闭连接/归还到池中
SQLAlchemy 的 Session 如果不 close()，连接不会归还到池中
"""

# 反面案例：Session 未关闭
def leak_connection_bad(session_factory):
    session = session_factory()
    result = session.execute(text("SELECT 1")).fetchone()
    # 忘记 session.close()，连接不会归还到池中
    return result

# 正确做法1：显式 close
def no_leak_good(session_factory):
    session = session_factory()
    try:
        result = session.execute(text("SELECT 1")).fetchone()
        return result
    finally:
        session.close()

# 正确做法2：使用上下文管理器（推荐）
from contextlib import contextmanager

@contextmanager
def get_session(session_factory):
    session = session_factory()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise
    finally:
        session.close()

# FastAPI 依赖注入方式（推荐）
from fastapi import Depends
from sqlalchemy.orm import Session

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/users/{user_id}")

    user = db.execute(
        text("SELECT * FROM users WHERE id = :id"), {"id": user_id}
    ).fetchone()
    return user
```

## 11.5 缓存策略（与第九章 Redis 互为补充）

### 11.5.1 Redis 缓存与数据库的一致性策略（性能角度）

在第九章 9.8 中我们详细讨论了缓存一致性的各种策略。这里从性能优化的角度做补充说明。

缓存的核心价值是"用内存换取磁盘 IO"。一次数据库查询需要磁盘 IO（即使有 Buffer Pool 缓存，高并发下缓存命中率也会下降），而一次 Redis 读取只需要内存访问（微秒级）。

```python
"""
缓存策略的性能对比示例
"""
import json
import redis
from sqlalchemy import text

r = redis.Redis(host='127.0.0.1', port=6379, db=0, decode_responses=True)

def get_product_without_cache(product_id: int, session):
    """无缓存：每次查数据库"""
    result = session.execute(
        text("SELECT * FROM products WHERE id = :id"),
        {"id": product_id}
    ).fetchone()
    return dict(result._mapping) if result else None

def get_product_with_cache(product_id: int, session):
    """有缓存：先查 Redis，未命中再查数据库"""
    cache_key = f"product:{product_id}"

    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)  # 缓存命中：微秒级返回

    # 缓存未命中：查数据库
    result = session.execute(
        text("SELECT * FROM products WHERE id = :id"),
        {"id": product_id}
    ).fetchone()
    if result:
        product = dict(result._mapping)
        r.setex(cache_key, 3600, json.dumps(product, default=str))
        return product
    return None

def monitor_cache_hit_ratio():
    """监控 Redis 缓存命中率"""
    info = r.info("stats")
    hits = info.get("keyspace_hits", 0)
    misses = info.get("keyspace_misses", 0)
    total = hits + misses
    hit_ratio = (hits / total * 100) if total > 0 else 0

    print(f"Cache hits: {hits}")
    print(f"Cache misses: {misses}")
    print(f"Hit ratio: {hit_ratio:.2f}%")

    if hit_ratio < 80:
        print("WARNING: Cache hit ratio is low. Consider:")
        print("  - Increasing cache TTL")
        print("  - Adding more keys to cache")
        print("  - Pre-warming cache for hot data")
```

### 11.5.2 Cache-Aside / Write-Through / Write-Behind 模式

#### Cache-Aside（旁路缓存）

最常用的缓存模式。应用层同时管理缓存和数据库。

```python
"""
Cache-Aside 模式
读流程：查缓存 -> 命中则返回 -> 未命中则查数据库 -> 写入缓存 -> 返回
写流程：更新数据库 -> 删除缓存
"""
def cache_aside_read(key, db_query_func):
    cache_key = f"cache:{key}"
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)
    data = db_query_func()
    if data:
        r.setex(cache_key, 3600, json.dumps(data, default=str))
    return data

def cache_aside_write(key, new_data, db_update_func):
    db_update_func(new_data)
    r.delete(f"cache:{key}")  # 先更新数据库，再删除缓存
```

#### Write-Through（直写模式）

应用写入时同时写缓存和数据库。缓存和数据库的数据始终同步。

```python
"""
Write-Through 模式
写流程：同时写缓存和数据库
读流程：只查缓存
"""
def write_through(key, data, db_insert_func):
    cache_key = f"cache:{key}"
    r.setex(cache_key, 3600, json.dumps(data, default=str))
    db_insert_func(data)
    # 如果数据库写入失败，需要回滚缓存
```

#### Write-Behind（异步写回模式）

写入时只写缓存，由后台异步刷入数据库。写入性能极高，但有数据丢失风险。

```python
"""
Write-Behind 模式
写流程：只写缓存，后台异步刷入数据库
风险：缓存宕机时未刷入数据库的数据会丢失
"""
import threading
import queue

write_queue = queue.Queue()

def write_behind_write(key, data):
    """只写缓存，加入异步队列"""
    cache_key = f"cache:{key}"
    r.setex(cache_key, 3600, json.dumps(data, default=str))
    write_queue.put((key, data))

def background_flusher():
    """后台线程：定期将队列中的数据刷入数据库"""
    while True:
        batch = []
        while not write_queue.empty():
            batch.append(write_queue.get())

        if batch:
            session = SessionLocal()
            try:
                for key, data in batch:
                    session.execute(
                        text("INSERT INTO ... VALUES (:data)"),
                        {"data": json.dumps(data)}
                    )
                session.commit()
            except Exception:
                session.rollback()
            finally:
                session.close()

        time.sleep(5)  # 每 5 秒刷一次

threading.Thread(target=background_flusher, daemon=True).start()
```

### 11.5.3 缓存穿透、缓存击穿、缓存雪崩的防御方案

这三个概念在第九章 9.8 已有详细解释，这里从性能优化角度补充实现代码。

```python
"""
缓存三大问题的防御方案实现
"""
import redis
import json
import time
import random

r = redis.Redis(host='127.0.0.1', port=6379, db=0, decode_responses=True)

# 1. 缓存穿透：查询不存在的数据，每次都穿透到数据库
# 防御方案：空值缓存
def get_product_with_anti_penetration(product_id: int, session):
    """防穿透的缓存查询"""
    cache_key = f"product:{product_id}"
    cached = r.get(cache_key)
    if cached is not None:
        if cached == "NULL":
            return None  # 空值缓存命中
        return json.loads(cached)

    result = session.execute(
        text("SELECT * FROM products WHERE id = :id"),
        {"id": product_id}
    ).fetchone()

    if result:
        product = dict(result._mapping)
        r.setex(cache_key, 3600, json.dumps(product, default=str))
        return product
    else:
        # 数据库也没有：缓存空值（短 TTL）
        r.setex(cache_key, 60, "NULL")
        return None

# 2. 缓存击穿：热点 key 过期瞬间，大量请求同时查数据库
# 防御方案：互斥锁
def get_hot_product_with_mutex(product_id: int, session):
    """防击穿：使用 Redis 互斥锁防止缓存重建并发"""
    cache_key = f"product:{product_id}"
    lock_key = f"lock:product:{product_id}"

    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)

    lock_acquired = r.set(lock_key, "1", nx=True, ex=10)
    if lock_acquired:
        try:
            result = session.execute(
                text("SELECT * FROM products WHERE id = :id"),
                {"id": product_id}
            ).fetchone()
            if result:
                product = dict(result._mapping)
                r.setex(cache_key, 3600, json.dumps(product, default=str))
                return product
        finally:
            r.delete(lock_key)
    else:
        time.sleep(0.05)  # 等 50ms
        return get_hot_product_with_mutex(product_id, session)

# 3. 缓存雪崩：大量 key 同时过期
# 防御方案：随机过期时间
def cache_with_random_ttl(key: str, data, base_ttl: int = 3600):
    """设置随机过期时间，避免同时过期"""
    random_offset = random.randint(-300, 300)
    actual_ttl = base_ttl + random_offset
    r.setex(key, actual_ttl, json.dumps(data, default=str))
```

### 11.5.4 查询缓存（MySQL Query Cache 的废弃，为什么不该依赖它）

MySQL 8.0 彻底移除了 Query Cache 功能。理解为什么移除它，有助于理解缓存设计的原则。

Query Cache 的工作原理：缓存完整 SELECT 语句及其结果集。当相同 SQL 再次执行时，直接返回缓存结果。

Query Cache 被移除的原因：

1. **命中率太低**：Query Cache 要求 SQL 完全一致（包括大小写、空格），实际应用中很难命中。`SELECT * FROM users WHERE id = 1` 和 `SELECT * FROM users WHERE id=1` 是两条不同的缓存键。

2. **写入开销大**：任何对表的写操作（INSERT/UPDATE/DELETE）都会使该表的所有 Query Cache 失效。在写多读少的场景下，Query Cache 成了负担。

3. **锁竞争严重**：Query Cache 使用全局互斥锁，高并发下成为瓶颈。

4. **替代方案更好**：Redis 等外部缓存更灵活、更高效、更可控。

前端类比：Query Cache 就像浏览器缓存中的"强缓存"——如果缓存策略配置不当，反而会导致用户看到过期数据或性能下降。MySQL Query Cache 的设计初衷是好的，但在实际使用中弊大于利，因此被移除。

### 11.5.5 物化视图（PostgreSQL）：预计算复杂查询

物化视图（Materialized View）是 PostgreSQL 的特色功能。普通视图（View）只是一个保存的查询语句，每次查询时动态执行。物化视图则会将查询结果物理存储到磁盘上，查询时直接读取存储的结果，不需要重新计算。

```sql
-- 普通视图（每次查询都重新计算）
CREATE VIEW daily_sales_view AS
SELECT
    DATE(created_at) AS sale_date,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount
FROM orders
WHERE status = 'paid'
GROUP BY DATE(created_at);

-- 物化视图（结果预先计算并存储）
CREATE MATERIALIZED VIEW daily_sales_mv AS
SELECT
    DATE(created_at) AS sale_date,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount
FROM orders
WHERE status = 'paid'
GROUP BY DATE(created_at);

-- 查询物化视图（直接读取存储结果，毫秒级）
SELECT * FROM daily_sales_mv WHERE sale_date >= '2024-01-01';

-- 在物化视图上建索引
CREATE INDEX idx_daily_sales_mv_date ON daily_sales_mv(sale_date);

-- 刷新物化视图
REFRESH MATERIALIZED VIEW daily_sales_mv;

-- 并发刷新（不锁定，可以同时查询）
CREATE UNIQUE INDEX idx_daily_sales_mv_unique ON daily_sales_mv(sale_date);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales_mv;

-- 更复杂的物化视图：多维销售分析
CREATE MATERIALIZED VIEW sales_analysis_mv AS
SELECT
    DATE(o.created_at) AS sale_date,
    p.category_id,
    c.name AS category_name,
    COUNT(*) AS order_count,
    SUM(o.amount) AS revenue,
    SUM(oi.quantity) AS units_sold
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
JOIN categories c ON p.category_id = c.id
WHERE o.status = 'paid'
GROUP BY DATE(o.created_at), p.category_id, c.name;

CREATE UNIQUE INDEX idx_sales_analysis_mv ON sales_analysis_mv(sale_date, category_id);
```

MySQL 没有原生物化视图功能，但可以通过以下方式模拟：

```sql
-- MySQL 模拟物化视图
CREATE TABLE daily_sales_cache AS

    DATE(created_at) AS sale_date,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount
FROM orders
WHERE status = 'paid'

ALTER TABLE daily_sales_cache ADD PRIMARY KEY (sale_date);

-- 定时刷新（使用事件调度器）
DELIMITER //
CREATE EVENT refresh_daily_sales
ON SCHEDULE EVERY 1 DAY STARTS '2024-01-16 02:00:00'
DO
BEGIN
    TRUNCATE TABLE daily_sales_cache;
    INSERT INTO daily_sales_cache
    SELECT DATE(created_at), COUNT(*), SUM(amount)
    FROM orders WHERE status = 'paid'
    GROUP BY DATE(created_at);
END //
DELIMITER ;
```

| 覆盖索引 | 8.0+ 支持 | 支持 | 索引包含查询所需所有列 |

```sql

-- GIN 索引（JSONB 全文搜索）

SELECT * FROM products WHERE attrs @> '{"color": "red"}';

-- BRIN 索引（大表近似索引，极小存储开销）
```

### 12.2.3 存储过程与函数

```sql
-- ============================================================
-- MySQL 存储过程
-- ============================================================
DELIMITER //
CREATE PROCEDURE transfer_funds(
    IN from_user BIGINT,
    IN to_user BIGINT,
    IN amount DECIMAL(12,2),
    OUT result VARCHAR(20)
)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET result = 'error';
    END;

    START TRANSACTION;
    UPDATE accounts SET balance = balance - amount
    WHERE user_id = from_user AND balance >= amount;
    IF ROW_COUNT() = 0 THEN
        ROLLBACK;
        SET result = 'insufficient_balance';
    ELSE
        UPDATE accounts SET balance = balance + amount WHERE user_id = to_user;
        COMMIT;
        SET result = 'success';
    END IF;
END //
DELIMITER ;

CALL transfer_funds(1, 2, 100.00, @result);
SELECT @result;

-- ============================================================
-- PostgreSQL 函数
-- ============================================================
CREATE OR REPLACE FUNCTION transfer_funds(
    from_user BIGINT,
    to_user BIGINT,
    amount DECIMAL(12,2)
) RETURNS VARCHAR AS $$
DECLARE
    affected INT;
BEGIN
    UPDATE accounts SET balance = balance - amount
    WHERE user_id = from_user AND balance >= amount;
    GET DIAGNOSTICS affected = ROW_COUNT;

    IF affected = 0 THEN
        RETURN 'insufficient_balance';
    END IF;

    UPDATE accounts SET balance = balance + amount WHERE user_id = to_user;
    RETURN 'success';

EXCEPTION WHEN OTHERS THEN
    RETURN 'error';
END;
$$ LANGUAGE plpgsql;

-- 调用（像调用函数一样）
SELECT transfer_funds(1, 2, 100.00);

-- 存储过程（PG 11+，支持事务控制）
CREATE OR REPLACE PROCEDURE batch_insert(count INT)
LANGUAGE plpgsql AS $$
BEGIN
    FOR i IN 1..count LOOP
        INSERT INTO test_data(val) VALUES (i);
        IF i % 1000 = 0 THEN
            COMMIT;  -- 存储过程内部可以 COMMIT/ROLLBACK
        END IF;
    END LOOP;
END;
$$;

CALL batch_insert(10000);
```

PostgreSQL 的存储过程语言更强大——支持 `IF/ELSE`、`LOOP`、`FOR`、`WHILE`、`EXCEPTION` 等完整控制结构，还支持用 Python、Perl、Tcl 等语言编写（通过扩展安装）。

### 12.2.4 触发器差异

```sql
-- MySQL 触发器
DELIMITER //
CREATE TRIGGER trg_orders_after_insert
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    INSERT INTO order_log(order_id, action, created_at)
    VALUES (NEW.id, 'created', NOW());
END //
DELIMITER ;
-- MySQL 限制：只支持行级触发，不支持语句级触发

-- PostgreSQL 触发器
CREATE OR REPLACE FUNCTION log_order_change()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO order_log(order_id, action, created_at)
        VALUES (NEW.id, 'created', NOW());
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO order_log(order_id, action, created_at)
        VALUES (NEW.id, 'updated', NOW());
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO order_log(order_id, action, created_at)
        VALUES (OLD.id, 'deleted', NOW());
        RETURN OLD;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- 行级触发器
CREATE TRIGGER trg_orders_log
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW EXECUTE FUNCTION log_order_change();

-- 语句级触发器（PostgreSQL 独有）
CREATE TRIGGER trg_orders_stmt
AFTER INSERT ON orders
FOR EACH STATEMENT EXECUTE FUNCTION count_inserts();
-- 每条 SQL 语句触发一次，适合批量操作后的统计更新
```

### 12.2.6 全文搜索能力对比

```sql
-- MySQL 全文搜索
```

## 12.3 性能特性对比

### 12.3.1 写入性能：MySQL 的优势场景

MySQL 在简单写入场景下通常比 PostgreSQL 更快，原因如下：

1. **存储引擎优化**：InnoDB 针对高频写入做了大量优化，Buffer Pool 的写缓冲（Change Buffer）能批量合并二级索引的更新
2. **更轻量的 MVCC**：InnoDB 的 Undo Log 实现比 PostgreSQL 的多版本存储更节省空间
3. **Group Commit**：MySQL 的组提交在批量写入时能合并 fsync 操作

```sql
-- MySQL 批量写入优化
INSERT INTO orders (user_id, amount, status) VALUES
(1, 100.00, 'paid'),
(2, 200.00, 'paid'),
(3, 150.00, 'pending'),
(1000, 99.00, 'paid');

-- MySQL 特有的 LOAD DATA INFILE（最快的批量导入方式）
LOAD DATA INFILE '/path/to/data.csv'
INTO TABLE orders
FIELDS TERMINATED BY ','
LINES TERMINATED BY '\n'
(user_id, amount, status);

-- 配置优化（写入密集场景）
-- my.cnf / my.ini
-- [mysqld]
-- innodb_buffer_pool_size = 4G        -- Buffer Pool 大小（物理内存的 50-70%）
-- innodb_log_file_size = 1G           -- Redo Log 大小
-- innodb_flush_log_at_trx_commit = 1  -- 每次事务提交都刷盘（最安全）
-- innodb_flush_log_at_trx_commit = 2  -- 每秒刷盘（性能提升，宕机可能丢 1 秒数据）
```

### 12.3.2 复杂查询性能：PostgreSQL 的优势场景

PostgreSQL 在复杂查询（多表 JOIN、子查询、窗口函数、CTE）方面通常优于 MySQL：

1. **更强大的查询优化器**：支持更多 JOIN 策略（Hash Join、Merge Join、Nested Loop）
2. **Hash Join 支持**：PostgreSQL 长期支持 Hash Join，MySQL 8.0 才加入
3. **并行查询**：PostgreSQL 9.6+ 支持并行查询，能利用多核加速
4. **更丰富的执行策略**：如 Index Only Scan、Bitmap Index Scan

```sql
-- PostgreSQL 并行查询示例
SET max_parallel_workers_per_gather = 4;

EXPLAIN ANALYZE
SELECT category_id, COUNT(*), SUM(amount)
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY category_id;
-- 输出会显示 Gather 节点，表示使用了并行扫描

-- Hash Join（不需要索引，适合大表 JOIN）
EXPLAIN ANALYZE
SELECT u.username, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.username;
-- PostgreSQL 可以使用 Hash Join，即使没有索引也能高效执行

-- CTE 优化（PostgreSQL 12+ 支持可内联的 CTE）
WITH heavy_users AS (
    SELECT user_id, COUNT(*) AS cnt
    FROM orders
    GROUP BY user_id
    HAVING COUNT(*) > 100
)
SELECT u.username, hu.cnt
FROM users u
JOIN heavy_users hu ON u.id = hu.user_id
ORDER BY hu.cnt DESC;
```

### 12.3.3 并发控制机制差异

| 维度 | MySQL (InnoDB) | PostgreSQL |
|------|-----------------|------------|
| MVCC 实现 | Undo Log + Read View | 多版本元组（xmin/xmax） |
| 旧版本存储 | Undo Log（独立空间） | 主表内（导致表膨胀） |
| 回滚开销 | 低 | 高（需要标记旧行为已删除） |
| 空间回收 | Purge 线程自动清理 | 需要 VACUUM 清理死元组 |
| 长事务影响 | 阻塞 Undo 清理 | 阻塞 VACUUM，导致表膨胀 |
| 读阻塞写 | 不阻塞 | 不阻塞 |
| 写阻塞读 | 不阻塞 | 不阻塞 |

```sql
-- PostgreSQL 的 VACUUM（MySQL 不需要）
VACUUM orders;                    -- 普通 VACUUM，不锁表
VACUUM FULL orders;               -- 完全回收空间，但锁表（慎用！）
VACUUM ANALYZE orders;            -- 清理 + 更新统计信息

-- 监控表膨胀
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup, 0), 2) AS dead_ratio
FROM pg_stat_user_tables
WHERE n_dead_tup > 0
ORDER BY n_dead_tup DESC;
-- dead_ratio 超过 10% 的表需要关注
```

### 12.3.4 存储引擎 vs 堆表的差异

MySQL 的核心架构特点是**存储引擎可插拔**——不同的表可以使用不同的存储引擎。PostgreSQL 则使用统一的堆表存储。

```sql
-- MySQL 存储引擎选择
CREATE TABLE orders (...) ENGINE=InnoDB;   -- 支持事务、行锁、MVCC
CREATE TABLE logs (...) ENGINE=MyISAM;     -- 不支持事务
CREATE TABLE temp_data (...) ENGINE=MEMORY; -- 数据存内存

-- PostgreSQL 没有存储引擎概念
-- 所有表使用统一的存储格式（堆表 + TOAST）
```

MySQL 存储引擎架构的影响：
- InnoDB：聚簇索引（主键即数据存储顺序），二级索引存储主键值（需要回表）
- MyISAM：非聚簇索引，数据和索引分离存储

PostgreSQL 的存储：
- 堆表：数据行无特定顺序存储在堆中
- 所有索引都是二级索引，都需要回表（通过 ctid 定位行）
- TOAST：大字段自动外存到 TOAST 表

### 12.3.5 大数据量下的表现对比

```sql
-- 场景：1000 万行订单表的聚合查询

-- MySQL:
-- 需要确保有合适的索引，否则大表聚合很慢
SELECT DATE(created_at), COUNT(*), SUM(amount)
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY DATE(created_at);
-- MySQL 需要索引支持 GROUP BY，否则出现 Using temporary; Using filesort

-- PostgreSQL:
-- 并行查询自动加速大表扫描
SET max_parallel_workers_per_gather = 4;
SELECT DATE(created_at), COUNT(*), SUM(amount)
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY DATE(created_at);
-- 可以使用并行 Seq Scan + 并行 Hash Aggregate

-- 大数据量下索引维护对比
-- MySQL:
ALTER TABLE orders ADD INDEX idx_user_created(user_id, created_at);
-- 大表加索引会锁表（8.0+ 支持在线加索引）

-- PostgreSQL:
CREATE INDEX CONCURRENTLY idx_orders_user_created ON orders(user_id, created_at);
-- CONCURRENTLY 模式：不锁表，允许并发读写
```

## 12.4 运维与生态对比

### 12.4.1 复制方案：MySQL 主从复制 vs PostgreSQL 流复制

#### MySQL 主从复制

MySQL 的复制基于 Binlog（二进制日志），从库读取主库的 Binlog 并回放。

```
主库 (Master) --Binlog Dump--> 从库 (Slave)
                                - IO Thread (写 Relay Log)
                                - SQL Thread (回放 Relay Log)
```

```sql
-- MySQL 主库配置 (my.cnf)
-- [mysqld]
-- server-id = 1
-- log_bin = mysql-bin
-- binlog_format = ROW
-- gtid_mode = ON
-- enforce_gtid_consistency = ON

-- 从库配置主库信息
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '192.168.1.100',
    SOURCE_PORT = 3306,
    SOURCE_USER = 'repl_user',
    SOURCE_PASSWORD = 'repl_password',
    SOURCE_AUTO_POSITION = 1;

START REPLICA;
SHOW REPLICA STATUS\G
-- 关注：Replica_IO_Running: Yes, Replica_SQL_Running: Yes, Seconds_Behind_Master: 0
```

#### PostgreSQL 流复制

PostgreSQL 的复制基于 WAL（Write-Ahead Log），从库实时接收主库的 WAL 流并回放。

```
主库 (Primary) --WAL Sender--> 从库 (Standby)
                                 - WAL Receiver (接收 WAL)
                                 - Recovery Process (回放 WAL)
```

```ini
# PostgreSQL 主库配置 (postgresql.conf)
wal_level = replica
max_wal_senders = 10
wal_keep_size = 1024
```

```sql
-- 查看复制状态
SELECT * FROM pg_stat_replication;
-- state=streaming 表示正在流式复制

-- 同步复制配置
-- synchronous_standby_names = 'FIRST 1 (standby1)'
```

复制方案关键差异：

| 维度 | MySQL | PostgreSQL |
|------|-------|------------|
| 复制方式 | Binlog -> Relay Log -> 回放 | WAL 流式传输 |
| 复制类型 | 异步/半同步 | 异步/同步 |
| 逻辑复制 | Binlog 有限支持 | 原生逻辑复制（Publication/Subscription） |
| 复制延迟 | Binlog 回放延迟 | WAL 回放延迟（通常更低） |

## 12.5 选型决策指南

### 12.5.1 中小型 Web 应用：MySQL 的简单够用

对于中小型 Web 应用（日活用户 < 10 万，数据量 < 千万级），MySQL 通常是更务实的选择。

```
适合 MySQL 的特征：
- CRUD 为主，查询不太复杂
- 表结构相对简单，JOIN 不超过 3-4 张表
- 团队更熟悉 MySQL（生态成熟，文档丰富）
- 需要快速上线，不想花太多时间在数据库调优上
- 预算有限，需要选择更便宜的云服务

典型场景：
- 内容管理系统（CMS）

- 用户管理系统
- 博客/论坛系统
- 中小型 SaaS 应用
```

### 12.5.2 复杂业务逻辑：PostgreSQL 的强大约束

当业务逻辑复杂，需要数据库层面保障数据完整性时，PostgreSQL 的优势凸显。

```
适合 PostgreSQL 的特征：
- 复杂的业务约束（需要 CHECK 约束、排他约束等）
- 大量复杂查询（多表 JOIN、窗口函数、递归 CTE）
- 需要存储过程实现复杂业务逻辑
- 需要高级数据类型（数组、JSONB、范围类型、地理空间）
- 对数据一致性要求极高

典型场景：
- 金融系统（强一致性、复杂约束）
- ERP 系统（复杂业务逻辑、多表关联）
- 地理信息系统（PostGIS）
- 复杂报表系统（物化视图、窗口函数）
- 多租户 SaaS（行级安全 RLS）
```

### 12.5.3 数据仓库/分析：PostgreSQL + 列式扩展

```sql
-- PostgreSQL + Citus（分布式扩展）：水平扩展
```

### 12.5.4 AI 应用：PostgreSQL + pgvector

随着 AI/LLM 应用的爆发，向量数据库成为刚需。PostgreSQL 通过 pgvector 扩展，在关系型数据库中实现向量存储和相似性搜索。

```sql
-- 安装 pgvector 扩展
CREATE EXTENSION IF NOT EXISTS vector;

-- 创建向量存储表
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    embedding VECTOR(1536),  -- OpenAI text-embedding-ada-002 维度
    metadata JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 创建向量索引（IVFFlat 或 HNSW）
CREATE INDEX idx_documents_embedding
ON documents USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);

-- 或使用 HNSW 索引（pgvector 0.5.0+，更高性能）
CREATE INDEX idx_documents_embedding_hnsw
ON documents USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 向量相似性搜索
SELECT id, content, metadata,
       1 - (embedding <=> :query_vector) AS similarity  -- 余弦距离
FROM documents
ORDER BY embedding <=> :query_vector
LIMIT 10;

-- 结合元数据过滤的混合查询
SELECT id, content
FROM documents
WHERE metadata @> '{"source": "api"}'  -- JSONB 过滤
  AND embedding <=> :query_vector < 0.5  -- 向量相似度过滤
ORDER BY embedding <=> :query_vector
LIMIT 10;
```

PostgreSQL + pgvector 的优势在于：你可以用一套数据库同时做关系型查询和向量搜索，不需要额外引入 Pinecone/Weaviate 等专用向量数据库。对于 LangChain/LangGraph 开发者来说，这极大简化了技术栈。

```python
"""
Python + pgvector + LangChain 示例
"""
from langchain_community.vectorstores import PGVector
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(
    model="text-embedding-ada-002",
    openai_api_key="your-api-key"
)

vectorstore = PGVector.from_documents(
    documents=documents,
    embedding=embeddings,
    connection_string="postgresql://user:pass@localhost:5432/aidb",
    collection_name="knowledge_base",
)

# 相似性搜索
results = vectorstore.similarity_search_with_score(
    query="如何优化数据库性能",
    k=5
)
```

MySQL 目前没有原生的向量类型和向量索引支持。对于 AI 应用开发者来说，PostgreSQL + pgvector 是目前最推荐的向量数据库方案之一。

### 12.5.5 团队技术栈匹配度

选型不能只看技术指标，还要考虑团队因素：

```
团队考量维度：

1. 团队熟悉度
   - 如果团队 80% 的人只会 MySQL，强行换 PostgreSQL 会导致开发效率下降
   - 但如果团队有学习能力且项目周期允许，PostgreSQL 的长期收益更高

2. 运维能力
   - MySQL 运维更简单，文档和工具更成熟
   - PostgreSQL 运维需要理解 VACUUM、WAL、序列等概念，门槛稍高

3. 生态匹配
   - 如果团队用 Django/SQLAlchemy，两个数据库都支持
   - 如果用 Supabase（BaaS），底层就是 PostgreSQL
   - 如果用 PlanetScale，底层是 MySQL（Vitess）

4. 招聘市场
   - MySQL DBA 更容易招到
   - PostgreSQL 的高级 DBA 相对稀缺但薪资更高
```

### 12.5.7 最终选型决策树

```
                        +---------------------------+
                        |  新项目数据库选型决策树    |
                        +---------------------------+
                                  |
                                  v
                    +--------------------------+
                    | 是否需要向量搜索/AI 功能？ |
                    +--------------------------+
                      | Yes              | No
                      v                  v
              +-------------+   +--------------------------+
              | PostgreSQL |   | 数据量是否超过千万级？     |

              +-------------+     | Yes              | No
                                  v                  v
                    +--------------------------+   +--------------------------+
                    | 是否需要复杂分析/报表？    |   | 业务逻辑是否复杂？        |
                    +--------------------------+   +--------------------------+
                      | Yes              | No         | Yes              | No
                      v                  v           v                  v
              +-------------+   +-----------------+  +-------------+   +----------+
              | PostgreSQL |   | 是否需要高并发   |  | PostgreSQL |   |  MySQL   |
              | + 分析扩展  |   | 写入（日志类）？ |  +-------------+   +----------+
              +-------------+   +-----------------+
                                  | Yes              | No
                                  v                  v
                          +----------+      +-------------+
                          |  MySQL   |      | PostgreSQL  |
                          | (写入快)  |      | (功能强)    |
                          +----------+      +-------------+

决策原则总结：
1. AI/向量搜索 -> PostgreSQL + pgvector
2. 复杂业务/强一致性 -> PostgreSQL
3. 大数据量分析 -> PostgreSQL + 列式扩展
4. 高并发简单写入 -> MySQL
5. 中小型 CRUD 应用 -> MySQL（够用就好）
6. 团队都不熟 -> MySQL（学习成本低）
7. 需要物化视图/部分索引/表达式索引 -> PostgreSQL
8. 只需要简单存储+Redis缓存 -> MySQL
```

**给前端转后端开发者的最终建议**：

如果你正在学习后端 Python 开发，并且目标是 AI 应用方向（LangChain/LangGraph），**强烈建议主攻 PostgreSQL**。原因如下：

1. pgvector 让你不需要额外学一个向量数据库
2. JSONB 完美契合前端开发者对 JSON 的熟悉感
3. FastAPI + SQLAlchemy + PostgreSQL 是 AI 应用开发的技术栈标配
4. Supabase 等 BaaS 平台底层就是 PostgreSQL，学一套技术栈可以用很久

但如果你接手的是已有 MySQL 项目，或者团队已经用 MySQL，也没必要强行换。MySQL 8.0+ 的功能已经足够强大，加上 Redis 配合，大多数场景都能应对。先用好手中的工具，再考虑是否需要迁移。
